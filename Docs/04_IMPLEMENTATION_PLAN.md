# Simple implementation plan: resume OCR, data confirmation, and segmentation

## 1. Scope and source of truth

Use `01_SYSTEM_LOGIC.md`, `02_BACKEND_FRONTEND.md`, and `03_APPLICATION_FLOW.md` as the MVP scope. The older `AI-FRS.txt` includes candidate registration, video analysis, and automatic recruitment; defer these to keep the first version small. Include OCR in the first version, replacing the existing documents' proposal to add it later.

Build an HR application that uploads a PDF resume, extracts information, lets HR confirm it, maps it to `AI_Fresher_Recruitment_Dataset_FINAL.csv`, and runs the model to group applications for review. This plan interprets “segment” as job-specific screening groups, not unsupervised clustering or automatic hiring.

The repository currently contains documentation, CSVs, notebooks, and a saved model; no frontend or backend application was found in the root listing.

## 2. End-to-end flow

```text
HR login -> Select active job -> Upload and preview PDF
 -> Extract embedded text; OCR scanned pages when needed
 -> Parse candidate fields -> HR corrects and confirms data
 -> Validate the 23-column application record
 -> Generate the model's engineered features
 -> Run saved pipeline with its saved threshold
 -> Show job-specific segment, model score, and evidence
 -> HR records a separate review decision
```

Do not run prediction on the initial extraction automatically. Reconfirm and recompute after edits to candidate data or job requirements.

## 3. Exact mapping to the final CSV

The final CSV has 23 columns. It is the raw application contract, not the complete model input schema.

| CSV field | Source and validation |
| --- | --- |
| Application ID | Generated by the application; never extracted from the resume |
| Candidate ID | Application-managed identifier; do not identify people by name alone |
| Job ID | Selected opening |
| Job Role | Selected opening |
| Degree | Resume education; HR confirms normalized degree |
| Specialization | Resume education; HR confirms |
| CGPA | Explicit resume value or HR entry; validate grading scale before normalizing to a 10-point scale |
| Class 10 Percentage | Explicit resume value or HR entry; range 0–100 |
| Class 12 Percentage | Explicit resume value or HR entry; range 0–100 |
| Backlogs | Explicit statement or HR entry; non-negative integer; absence is unknown |
| Skills | Extracted skills, normalized using a small alias dictionary; HR confirms |
| Number of Projects | Count confirmed distinct project entries |
| Projects | Confirmed project titles |
| Number of Internships | Count confirmed distinct internship entries |
| Internships | Confirmed internship titles |
| Number of Certifications | Count confirmed distinct certification entries |
| Certifications | Confirmed certification titles; extraction does not establish authenticity |
| Number of Achievements | Count confirmed distinct achievement entries |
| Achievements | Confirmed achievement entries |
| Number of Openings | Selected opening; positive integer |
| Required Skills | Selected opening; non-empty for skill-match computation |
| Preferred Degree | Selected opening |
| Minimum CGPA | Selected opening; compatible with the confirmed grading scale |

Keep lists as arrays internally and serialize them as comma-separated strings only at the CSV/model boundary. Use a CSV writer so embedded commas are quoted correctly. Keep names, contact details, source-page evidence, and OCR warnings outside the 23-column model record.

Missing is different from zero. An absent projects section does not confirm zero projects. Preserve nulls until reviewed. For the first model integration, incomplete model inputs go to `Needs Data Review`; do not invent grades, assume zero backlogs, or silently replace missing numeric values with zero.

## 4. Minimal extraction and OCR

- Accept PDF only initially, including PDFs containing scanned pages.
- Validate file size, signature, readability, and access permissions; store under a generated filename outside public frontend assets.
- Extract text page by page with PyMuPDF. OCR pages with no usable text using Tesseract through a Python adapter. This also supports mixed text/scanned PDFs without OCR on every page.
- Detect pages where text exists but is unusable; allow an explicit retry with OCR. Preserve page order and avoid concatenating duplicate OCR and embedded text.
- Start with section headings, regular expressions for grades/contact details, and a curated skills dictionary. OCR supplies text; the parser maps that text into fields.
- Show the original PDF beside an editable extraction form. Display source page/text where available and flag ambiguous or missing values. Do not claim parser confidence unless it has a defined calculation.
- If extraction fails or OCR produces poor output, allow correction/manual entry and keep prediction blocked until the record is valid.

## 5. Model integration and existing issues to resolve

`06_ML_Model.ipynb` saves a dictionary containing `pipeline`, `model_name`, `threshold`, `feature_columns`, and `target`. Its recorded training input has 34 columns. Inspect the actual local artifact's metadata during implementation and validate it against the adapter before enabling inference; this plan has not loaded or executed the artifact.

Build a single feature adapter shared by training and inference:

- Remove Application ID, Candidate ID, and Job ID from prediction inputs.
- Preserve the remaining 20 raw input columns and derive the 14 engineered fields used in training.
- Derive `CGPA_Score`, `CGPA_Eligible`, `CGPA_Gap`, `Degree_Match`, and `Skill_Match` using the training definitions.
- Derive `Project_Count`, `Internship_Count`, `Certification_Count`, `Achievement_Count`, and `Backlog_Score`.
- Derive `Project_Score`, `Internship_Score`, `Certification_Score`, and `Achievement_Score` using frozen training normalization constants. Never recompute maxima from an uploaded resume or the current applicant batch.
- Match the artifact's exact column names, order, types, category serialization, and threshold. Use the saved pipeline rather than fitting preprocessing during a request.
- Exclude `Recruitment_Score`, `Rank`, `Shortlist Limit`, and `Shortlisted`; these are label-related fields, not prediction inputs.

Resolve these compatibility issues before exposing model results:

1. The feature notebook normalizes counts using dataset maxima but the shown save code does not store those constants. Recover and freeze the original constants if reproducible; otherwise rebuild the artifact with versioned preprocessing metadata.
2. The ML CSV contains a visible malformed empty project value (`N, o, n, e`). Fix missing-list serialization in the shared preprocessing and retrain if input semantics change; preserve the original CSV files.
3. The training labels are generated from a weighted score, random noise, per-job rank, and a shortlist limit of approximately 3.5 times openings. This is a synthetic shortlist classifier, not a validated hiring predictor or clustering model.
4. The notebook's recorded shortlist-class test precision/recall are about 0.47/0.59 despite about 99% overall accuracy. Validate minority-class performance and job-level results before relying on the output.
5. `07_Model_Analysis.ipynb` uses another feature setup. Follow the saved artifact contract rather than mixing notebook pipelines.

If the model contract is unavailable or incompatible, keep extraction/review usable and show `Model unavailable`. A transparent job-match score can be shown separately as described in the system document; never label a fallback score as a model prediction.

## 6. Simple segments and result screen

Apply these rules in order:

| Segment | Rule |
| --- | --- |
| Needs Data Review | Missing required model inputs, ambiguous values, or unconfirmed extraction |
| Potential Match | Valid confirmed record; positive-class model score meets the saved threshold |
| Lower Model Match | Valid confirmed record; score is below the saved threshold |

Keep processing failures separate from these candidate segments. A model failure receives a processing error, not a low-match label. Model probability is an uncalibrated model score unless calibration is demonstrated; it is not a probability of hiring success.

For each selected job, display candidate reference, segment, model score, matched/missing skills, education summary, extraction warnings, and HR review status. Order scored applications within that job by model score, using a stable identifier as a tie-breaker. Keep incomplete records in a separate review list. Recompute ranking when applications change. Segments do not automatically fill openings, reject candidates, or change HR decisions.

## 7. Minimal application structure

Frontend: React + Vite with login, job openings, upload/preview, extraction review, results/history, and a small dashboard. Use simple tables and counts before adding charts.

Backend: FastAPI, Pydantic validation, PDF extraction/OCR service, parser, shared feature adapter, and model service. Start with one service process and simple status polling; avoid a separate queue service initially. On restart, surface interrupted work for retry rather than leaving it permanently processing.

Suggested screening API additions to the existing API plan:

| Endpoint | Purpose |
| --- | --- |
| `POST /api/screenings` | Upload PDF with selected job and begin extraction only |
| `GET /api/screenings/{id}/status` | Actual extraction/OCR/validation progress |
| `GET /api/screenings/{id}` | Extracted data, warnings, confirmation state, and available result |
| `PUT /api/screenings/{id}/data` | Save reviewed data and confirm a valid version |
| `POST /api/screenings/{id}/predict` | Generate features and segment the confirmed version |
| `GET /api/screenings?job_id=...` | Filter history and segments by opening |
| `PATCH /api/screenings/{id}/review` | Record HR decision separately |

Protect resume retrieval and all HR operations with authentication. Keep original files, candidate data, and credentials out of Git and application logs.

| 1. Data contract and model adapter | Validated 23-field schema, mapping, saved-model inspection, frozen feature metadata | A complete known application produces the expected 34-column input; missing inputs block prediction |

| 6. Verification | Targeted adapter, extraction, missing-data, API access, and end-to-end checks | Feature parity and reviewed text/scanned resume examples pass; model limitations are displayed accurately |

Use synthetic fixtures only in isolated tests, never as dummy records in an application database. Build the first extraction-to-model path before adding dashboard polish.
